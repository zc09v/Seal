# 项目愿景
解决llm应用开发中的结构化输出保证问题。
问题：前端/下游系统依赖模型产生严格结构，但模型输出不稳定，导致逻辑、流程异常
现状不足：现有依赖解析/正则或用 model-guided parsing，但缺少针对结构化 contract 的通用运行时校验与 fallback。
期望库具有如下能力与特点：
<ol>
<li>轻量级：仅包含最基础和必要的能力，避免引入额外依赖或复杂设计</li>
<li>schema/contract的标准化支持</li>
<li>保证结构合法：需要保证的不仅是“格式合法”（valid JSON），还包括字段语义正确性、类型/枚举有效性、约束（比如价格 >= 0）、必需字段存在，以及按业务规则一致性（start_date <= end_date</li>
<li>具有运行时模型修正、重试、回退、度量（如违背率、修复成功率）、审计(每一次修复的来源与证据)等能力</li>
</ol>

# 工作流程与规范
## 编码前
<ul>
<li>
仔细阅读已有的设计文档(中文)，包括架构设计文档（./seal/dev_md/designs/architecture_design.md）及任务相关的模块设计文档（./seal/dev_md/designs/xxxx_module_design.md,xxxx为模块名称）。
</li>
<li>文档设计</li>
先输出方案设计文档(中文)，包括功能描述、接口设计、数据库设计、文件目录结构等，并以md格式文件输出到./seal/dev_md/designs文件夹下(模块设计文档命名规则xxxx_module_design.md，xxxx为模块名称)

**重要：待我确认方案无误后再进行具体的编码!**
<li>设计原则</li>
<ul>
<li>SOLID原则</li>
<li>

**原则上仅考虑最基础和最必要的能力，避免引入额外依赖或复杂设计**
</li>
<li>注意模块的分层与解耦</li>
</ul>
</ul>

## 编码中
<ul>
<li>

**重要：使用纯英文进行编码，包括注释**
</li>
<li>代码都放到./seal/codes目录下，按模块合理组织</li>
<li>注意格式、注释、命名规范等，注释务必详尽、清晰</li>
<li>如果需要llm api账号信息，可以在development_guide.md "账号信息"部分找到，找不到的话联系我</li>
<li>不仅要满足于功能需求，还要全面考虑代码的复用性、可维护性、可扩展性、可测试性等方面</li>
<li>需要开发或调整对应的单元测试代码，以确保质量，测试文件按模块都统一创建在./tests/codes/xxxx目录下，xxxx为模块名称</li>

<li>

**重要：注意将代码的编写粒度尽可能拆细，不要一次就将所有功能都完成，完成相对独立、完整的一部分后，就可以进行编译、测试，并交给我review，待没问题后再继续**
</li>
</ul>

**重要：记得每次修改后，及时更新方案设计文档，确保与当前代码实现保持一致**
</li>
<li>

**重要：代码如果有调整，要关注所有关联逻辑（调用处）的适配修改**
</li>
</ul>
